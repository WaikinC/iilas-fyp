# Automatic, locked business codes

2 November 2026, Malaysia. Status: **approved by the user**; the Native implementation plan is prepared for review. Product implementation and live activation have not started. Native execution is the user's existing preference. The fresh independent builder check returned **nothing important left**.

## Intent and chosen approach

The user wants staff to stop inventing identifiers while adding products or creating orders. After the cross-module audit and publication of Reports graphs, the user selected **“Always generate and lock the codes.”**

Two approaches were presented: generated defaults with an existing-code override, or compulsory generated/locked codes. The user chose the latter. New products, shipments and purchase orders therefore receive their business code from the trusted MSI backend. The browser cannot choose or replace it. Existing stored codes remain exactly as they are and become read-only in these editing workflows; records are not renumbered.

This is a cross-module creation/recovery change rather than a cosmetic disabled-field change. Counter allocation, uniqueness and recovering an uncertain save must agree in one transaction. The existing React/Firebase/Spark/MSI architecture is retained.

## Scope and visible behaviour

Proposed formats below are builder decisions for this design, rather than formats previously specified by the user:

| Record | Locked business field | Format | Example |
|---|---|---|---|
| Product | `sku`, displayed as Item code / SKU | `PRD-` plus six digits | `PRD-000001` |
| Shipment draft | `reference`, displayed as Shipment reference | `SHP-` plus six digits | `SHP-000001` |
| Purchase order, ordinary or stock-AI-linked | `reference`, displayed as Purchase order reference | `PO-` plus six digits | `PO-000001` |

Each sequence belongs to the one shared system's existing data scope. Sequences do not reset by year and are separate by kind. Valid numbers are 1–999,999; exhaustion refuses creation with a clear administrator message. No guarantee of gapless numbering is made. Successfully issued numbers are never recycled after cancellation, archiving or deletion.

Creation forms show **Assigned automatically when saved** in place of an editable code field. They do not display a guessed next number or allocate one when a dialog opens. After success, the actual code appears in the success notice and record details, available for selection/copying. Editing shows the stored code as read-only, including legacy codes. Existing navy/purple controls, tab navigation, form grouping, status colours and focus behaviour remain.

The product's barcode remains its existing separate scanned/entered field with the current 8–14 digit validation and uniqueness check. The choice approved by the user concerned SKUs and shipment/PO references; this design does not fabricate a manufacturer's barcode or add a new barcode-generation/label-printing feature. Supplier delivery-note/receipt references, vehicle plates, licences, names, addresses and other factual information remain entered or selected normally. This barcode boundary is called out for the user to review.

## Other modules

- Warehouse handovers retain their existing generated `PS-{shipment.reference}` relationship and immutable item snapshots. Existing handovers are untouched.
- Stock movements, delivery events, evidence, AI requests/results and retained integrity checks keep their existing generated database/request identities. Their meaningful external document references remain separate.
- Transport, delivery, customer access, reports and exports reuse the stored shipment/product/PO codes. They do not allocate a second identifier for the same business record.
- Fleet resource/event database IDs and Firebase account UIDs remain automatic. Physical vehicle registrations/licences and email identities are not generated by this feature.
- Internal Firestore document IDs remain separate opaque IDs. They are not replaced by sequential business codes, and knowing a code grants no additional access.

## Trusted allocation and uniqueness

Introduce a private versioned numbering policy, a private counter per scope/kind and an immutable generated-code assignment. Exact collection names are a planning decision, but all are backend-only. Client SDK reads/writes to counters, assignments and private creation receipts are denied. Roles, active approval and the authoritative `system/config.dataScopeId` are checked inside the transaction; caller-supplied scope or role is not trusted.

For a new record, the backend validates the creation payload without accepting `sku`/`reference` as an input. It then reads its numbered policy/counter, uniqueness reservations, relevant supplier/product/warehouse facts and operation receipt. Before any writes it selects the next valid number and verifies that the code is not claimed by another record. It atomically writes the record, existing unique-key reservation, new immutable code assignment, incremented counter, creation receipt and existing audit history. All Firestore transaction reads precede writes, including existing purchase-transition reads.

The existing product barcode reservation, shipment unique-key protection and procurement reference reservation remain in force. A code conflict never overwrites a record/reservation. An inconsistent counter/assignment or exhaustion fails closed rather than allowing manual entry. Limited transaction retries for concurrent staff submissions may pick different unused numbers; a successful commit has exactly one code and one record.

Code updates are rejected on the backend for both new generated records and legacy records. A hidden form field, direct API call, stale tab or replay cannot rename one. Existing generic `save`/ordinary purchase creation must not remain a route for manually supplied codes after cutover. Product/shipment editing and other purchasing actions retain their version and permission contracts.

## Recoverable creation

Product, shipment and ordinary purchase creation currently lack the complete recoverable numbering contract needed here. Each new creation uses an immutable operation UUID saved before sending and a private receipt bound to environment/project, scope, actor, kind and canonical creation input. A repeated UUID with different input is refused. The record ID can be generated before transaction retries, but is bound permanently by the successful receipt.

Normal creation roles remain unchanged. Resolution requires current approved account access and the original actor/scope; a changed approved role can recover its original outcome without permission to create another record. Another actor cannot claim the receipt. Disabled/unapproved accounts remain denied.

The client retains one pending operation per creation kind and exposes **Check outcome**, **Retry saved creation**, and a safe cancellation option where the transaction contract supports it. A lost reply, reload, modal dismissal or navigation cannot silently create a fresh request. Input remains immutable while outcome is unknown. Account changes hide the previous user's draft/pending data, and original-account recovery remains available after signing back in.

If no receipt exists yet, identical resubmission uses the same operation UUID. Cancellation must transactionally create a terminal cancellation receipt so a concurrent late creation cannot succeed afterwards; it allocates no number. If creation won the race, resolution returns the existing ID/code. This is not a browser-only “clear” operation. A subsequently deleted or archived record does not cause its saved creation to be recreated or assigned a new code; the outcome explains its later availability separately.

Stock-AI-linked purchasing retains its existing accepted requirement, operation identity, source fingerprint, independent approval and expected-incoming/receipt contracts. Only creation's reference source changes to trusted allocation. Previously saved linked-purchasing operations remain recoverable under their exact old input, including their historical reference; they cannot be rewritten to the new schema or start a second PO. A versioned decoder distinguishes new code-free creation intents from historical recovery-only intents. Historical reference-bearing intents may resolve/replay a previously committed outcome, but cannot start a new manually referenced order after activation.

## Existing data and numbering initialization

No existing product/shipment/PO code, ID, quantity, reservation, ledger, approval, evidence link or handover is changed. The selected Admin and shared staff scope remain fixed; no personal inventories are merged.

Before activating numbering on an existing database, perform three bounded scope-filtered projections of product SKU, shipment reference and PO reference, retaining IDs/code/version only in private local evidence. Include archived products and all statuses. Normalize code comparison without changing stored casing. Validate completeness with a one-record lookahead; the initial cap is 2,000 records per kind. If exceeded or ambiguous, stop and plan a separately bounded initialization rather than silently sampling or scanning all unrelated collections.

Initialize each counter above the highest existing normalized exact generated-format code in its namespace. For example, an existing `PRD-000017` means the next product number is at least 18. Nonmatching legacy references remain unchanged. Case variants, missing old uniqueness keys and existing reserved codes must be considered in initialization; inconsistent existing claims must be reported rather than repaired by renaming. Retain existing generated-code assignments/counters when the policy is already present; never reset or overwrite differing configuration.

Activation must close the race with old clients: stop the trusted API, verify the bounded code baseline again, apply the reviewed numbering initialization with exact source/config guards, then start the new backend which refuses old manual-create requests. A differing baseline is refreshed/reviewed before initialization. Missing numbering configuration refuses new creates while preserving existing read/edit/recovery paths. A brand-new disposable emulator system can initialize zero counters through its trusted bootstrap because its scope has no existing records; no browser may invoke an unrestricted initializer.

## Verification

Meaningful checks must cover:

1. Parallel creation by two approved staff yields unique monotonic codes and one assignment per record. Aborted validation/transactions allocate nothing; committed cancelled/archived/deleted records do not free a number.
2. Lost replies, repeated HTTP submissions, reload recovery, operation-ID input mismatch, cancellation races, account changes and changed roles preserve one ID/code and prevent duplicates.
3. Client-supplied codes, attempts to edit generated or legacy codes, foreign scopes, unapproved users and inappropriate roles are denied through the actual backend and Firebase rules.
4. Existing manufacturer barcode validation/uniqueness, product balances and per-location accounting, warehouse handover/packing locks, exactly-once dispatch, independent PO approval and partial/full stock receipts remain correct.
5. Both ordinary and demo-linked purchasing use automatic references; historical saved operations resolve exactly and cannot bypass the new creation policy.
6. Initialization handles existing generated-looking codes, case variants, absent legacy reservations, preserved existing policy, bounded overflow and concurrent baseline changes. No existing record is renumbered.
7. Desktop/narrow forms show the generated state clearly, focus the correct validation error, preserve recovery across tabs and expose actual stored codes in lists/details/reports/CSV. Phone and parcel trials remain deferred.

Run build, lint, tracked/history secret scans, both original Firebase regressions and affected creation, warehouse, dispatch and purchasing suites sequentially on explicit loopback emulators. Use registered fictional fixtures with exact cleanup. Do not connect these suites to cloud data or start a second emulator stack.
