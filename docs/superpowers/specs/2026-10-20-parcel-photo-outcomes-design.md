# Parcel photo requests and recoverable outcomes

Status: implementation design for the authorised parcel-first goal; not implemented or verified by this document. The expanded training experiment is running independently. Its seven bound research files, manifest, protocol and existing results must remain unchanged.

## Intended outcome

An approved staff member selects a registered parcel photograph for the appropriate shipment stage, explicitly requests analysis, and can recover the exact saved outcome after a lost response or page reload. A duplicate submission cannot create a second inference or prediction for the same operation. Results name the image, stage and evaluated model used. Unavailable, failed, expired and abstained outcomes never appear as Normal. Human review remains mandatory.

The report requires uploaded-image and camera analysis. This increment completes the photo request lifecycle; repeated sampled camera sessions follow separately. It preserves the shared Admin/staff system, existing IDs and balances, Prepared-Shipment Handover and current interface. Inventory/delivery model development and additional features remain deferred.

The current `predict` handler stores successful labels but has no durable parcel operation identity, unavailable/abstained outcome or recovery receipt. It uses the delivery permission group, which excludes Warehouse staff even for their Prepared pre-dispatch photos. Stage-linked evidence already exists. The new parcel path must use the existing stage/access matrix, rather than extending the tabular prediction path or changing stock/handover behavior.

## Approach

Use the existing trusted Functions command boundary with Firestore transactions around one synchronous bounded Python call. A private operation receipt claims execution before remote work; a scoped public analysis record exposes its safe state. Repeating an operation returns its current outcome without calling Python again. A second command resolves a saved operation after response loss. Explicit expiry prevents a crashed request from remaining Running forever and fences late completion.

The old `predict(kind='parcel')` entry must reject with a clear request-workflow error; it must never retain a successful legacy bypass. Remove parcel submission from the generic ResearchVerification form and route parcel actions through the new evidence-level workflow. Keep existing saved predictions readable/reviewable and preserve inventory/delivery commands and forms unchanged.

Alternatives considered: retaining the current successful-predictions-only collection cannot recover failed/ambiguous requests; a task queue introduces a separate worker/deployment lifecycle and is unnecessary for one bounded photo call. Keep the current request transport and fail closed while no model is accepted.

## Identity and records

The browser creates a UUID operation ID before its first submission. Its persisted same-tab intent contains only actor, fixed scope, evidence ID and operation ID; never image bytes, tokens or configuration. Do not replace it on timeout. Keep the intent until a terminal outcome or explicit safe dismissal. Clearing browser storage cannot erase the server record; authorised staff can still see scoped saved analyses.

The trusted server derives the fixed scope and actor. A private `parcelAnalysisRequests` receipt is keyed by a hash of scope, actor and operation ID; it stores the immutable command hash, public analysis ID, captured evidence/stage bindings, claim nonce, start/expiry times and terminal state. No client reads/lists/writes this collection. The public `parcelAnalyses` record contains ownerId, analysis ID, actor, operation ID, shipment/evidence IDs, evidence version/hash, stage, shipment version at request, source/capture declaration, state, timestamps and safe outcome provenance. A private evidence lock binds scope, evidence ID, analysis ID, receipt key, nonce and expiry. Every release checks every ownership coordinate; a predecessor cannot delete a successor's lock. No storage paths, service URLs, credentials, stack traces, raw images or arbitrary service messages appear in public records.

21October review clarification: a new operation that encounters an active evidence lock must atomically save a private immutable `Blocked` receipt binding its scope/actor/operation ID, command digest and evidence ID to the original blocking public analysis ID. It owns no analysis lease, nonce or evidence lock. A matching start replay always returns the same safe Busy response, including after the blocking analysis has become terminal; it can never turn into a new inference claim. The browser still persists only its four IDs. After reload, an explicit Check can recover that fixed Busy reference through same-operation replay; a later explicit Check resolves that historical analysis. Only after learning a terminal outcome may the browser clear its saved intent and allow a separately explicit new operation. A different input with the same operation ID still rejects. This durable server behavior is required for recovery; memory-only client Busy state cannot provide it.

Terminal states are `Predicted`, `Abstained`, `Unavailable`, `Failed`, `Stale` and `Expired`. Only Predicted carries a Normal/Damaged label. Abstained has a null label and may carry validated scores/model provenance. Unavailable/Failed/Stale/Expired carry a null label and a fixed safe reason code. Running has no result. Do not invent scores for any failed or missing inference.

## Trusted commands and transitions

1. `startParcelAnalysis` accepts only evidence ID and UUID operation ID. Reject extra caller-supplied result, model, identity, stage or resource fields. In a transaction, first recheck current approval/activity/fixed-scope shared-read access and look up this actor's existing operation. A matching command hash returns its safe saved state without remote work even if stage/role/assignment changed; a different command hash is rejected. Historical replay is not permission to start a new analysis.
2. Only for a new operation, enforce current stage-aware role, immutable image provenance and shipment state/assignment. Unknown legacy stage is viewable but cannot enter a new current-stage request. Snapshot the requesting account version, current shipment version, evidence version/hash, transport-plan presence/version/assigned driver, and exact acceptance pin identity. Create Running with a server-owned nonce and a 90-second lease. A private evidence-level lock prevents simultaneous active operations for the same evidence. If blocked, atomically save the immutable Blocked receipt described above and return only a safe busy reason and blocking public analysis ID so authorised staff can use Check outcome; never expose private key/nonce. Resolving expiry does not automatically launch a replacement. No background queue or automatic replacement call is introduced.
3. After claim, check the trusted acceptance pin and service configuration before downloading any image. With no accepted model, finish as Unavailable with a safe reason and no prediction. This records the real unavailable workflow without opening the acceptance gate.
4. For an admitted model, stream the registered immutable bytes under the 10 MiB limit, verify recorded length/type and SHA-256, and call the authenticated bounded service once. Do not use an unbounded Storage download or response.json(). Enforce a 10-second Storage deadline, a 30-second HTTP deadline including body reading, a 16 KiB response-body cap and a 50-second overall handler budget, leaving time inside the current 60-second Function limit to persist a terminal outcome. Abort/close streams on limit, deadline or failure. Content-Length alone is insufficient. Validate the complete response against the exact accepted model, registered image, scores, explicit ['Normal','Damaged'] class order, preprocessing, selection/evaluation/acceptance digests and bounded timings. Coordinate the Python response/admission schema and its software tests before allowing these new fields; no operational pin is populated here. Store the service-generated request ID separately from the application operation ID.
5. Completion uses a transaction that requires the same Running receipt/nonce, unexpired lease and matching evidence lock. Recheck current approval, activity, role, fixed scope, stage/status and assignment, plus exact equality of the claimed account, shipment, evidence and transport-plan snapshots (including absence/presence and version), evidence hash and accepted pin identity. This catches a context change even if a role or assignment was subsequently restored. A change cannot save a label or a legacy prediction. Record only an appropriate safe terminal failure; public inferred-result writes require final authorised state.
6. Successful valid results atomically terminalise the receipt and public analysis, release the evidence lock and create at most one legacy `predictions` projection plus audit for Predicted. Use a deterministic prediction ID derived from analysis ID. Bind the projection to analysis ID, shipment/stage, full model/evaluation/image provenance and uncalibrated confidence. Abstained creates no Normal/Damaged projection.
7. `resolveParcelAnalysis` accepts only public analysis ID. It rechecks current Approved/active fixed-scope shared-read access and returns the safe saved outcome; it does not require the original actor, current upload role, shipment stage or assignment. Thus authorised staff can recover a historical result or expire an abandoned request after dispatch/reassignment. It never retries inference. Completion requires serverNow < expiresAt; expiry requires serverNow >= expiresAt. When a Running lease has expired, resolution atomically marks Expired and releases only its matching lock; a later remote response cannot commit. Every terminal inference state/result is immutable; only the separate authorised review fields may change with version checks. A new explicit operation may be submitted only after the old outcome is terminal. Expired means no authoritative result was saved, not proof that remote computation never occurred.

Lost-access completion must not publish an inferred label or overwrite a successor lock. An exception thrown from a Firestore transaction rolls its writes back. If authorised completion is rejected, a separate server-internal finaliser may terminalise the original matching Running receipt and public record to a fixed null-result failure, and release only its matching lock. It derives identity from the already-claimed receipt, accepts no caller result fields, and can never persist probabilities/model output on this path. This server housekeeping prevents an orphaned public Running state without restoring a revoked user's read access or business-write permissions.

Firestore transaction callbacks contain reads/writes only; Storage and HTTP work occur once outside retries after a committed new claim. The claim stores a server-derived canonical digest and safe selected-model identifiers for the exact validated acceptance descriptor, or null when absent. A result cannot complete under a different descriptor. Terminal Predicted creation requires both the deterministic projection ID and associated result/audit to be absent; inconsistent existing records fail closed rather than being overwritten. External service, Storage, parser, transaction and resource exceptions map to a fixed safe reason/message set. Callable details may contain only state, public analysis ID and safe reason code; never raw exception text or private paths/keys.

## Review and interface

Keep the evidence list and existing navy/purple layout. Add Request analysis and Check outcome actions, a visible image/stage binding, pending state, safe failure explanation and explicit mandatory human review. Use the same role/status policy as stage acquisition: Warehouse is eligible for Pre-dispatch/Prepared; assigned Driver is eligible for Delivery/Dispatched. Viewer and Inventory cannot start analysis. Previously saved records remain historical after the shipment changes, but cannot be presented as a new assessment of its current condition.

Predicted analysis links to the existing reviewed prediction. Accept/Reject review updates must atomically keep the analysis and prediction projection consistent, with version checks and Admin/Manager review authority. Extend the existing prediction review path for linked analyses; preserve its historical unlinked predictions. For Abstained, a dedicated Admin/Manager review action accepts analysis ID, version and required notes, marks reviewStatus Reviewed and records reviewer/time. It keeps the AI label null and does not create a prediction or human-labelled training datum. Until that action occurs, show Human review required. Do not add a new manual condition-label collection in this increment.

At Predicted creation, both linked records have reviewStatus Pending and reciprocal IDs. Any subsequent Accept/Reject transaction reads and validates both records, their reciprocal IDs, original result/evidence bindings and Pending review states, then updates both review fields/versions atomically. A broken link cannot be reviewed into validity. Historic unlinked predictions retain the old review contract.

For current parcel dashboard summaries, require a reciprocal Predicted analysis/projection pair with Accepted human review, matching evidence version/hash and a known stage that matches current shipment lifecycle (Pre-dispatch/Prepared or Delivery/Dispatched). Null-label, Pending, Rejected, stale and legacy unlinked results stay in appropriate historical/review lists and do not count as current accepted parcel assessments. Do not infer a stage for old records or change inventory/delivery summary predicates. The eight-card layout and its other counts remain intact.

The UI keeps a saved intent when an HTTP response is ambiguous, serialises Check outcome with submission, and rejects late responses after actor/evidence/stage changes. Navigation releases camera streams as already implemented. A disabled service is displayed as unavailable; no simulated label or acceptance bypass is permitted.
