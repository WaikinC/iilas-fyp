## Review Focus

1. Same Firebase project ID in two modes, changed backend instance, account switch or old native queue: no SDK reuse, deletion, silent migration or replay against a different destination (Tasks1,5,6).
2. Process death between byte/manifest commits, disk exhaustion or finalisation races: never expose incomplete bytes, overwrite a generation or retain an obsolete authority result (Tasks3–4).
3. Transaction commits before a dropped reply, role loss or outage: resolve the original saved operation; timeout does not undo it and ordinary commands are not automatically retried (Tasks2,5,9).
4. Stale backup, selected-UID/config/Hosting change or other-owner inventory: stop adoption/cutover and preserve all unrelated records; no wholesale restore/import (Tasks1,8,10).
5. Wrong credential/project, unexpected Origin, partial deployment, provider failure or enabled billing: refuse without fallback to emulator, CLI credentials, billed services or broader public ports (Tasks1–2,8–10).

### Shared contracts fixed by this plan

- `SparkProfile` is a closed object: `{schema:'iilas-spark-msi-1.0', mode:'spark-msi', projectId, webOrigins, apiOrigin, backendInstanceId, adoptionSha256, evidenceStore:'msi-local'}`. Project is the exact existing ID; origins are unique HTTPS origins with no path/query/credentials, only the exact approved Hosting origin initially. Instance is a persistent UUIDv4; digest is64lowercase hex. No bucket/region, secret, filesystem path or emulator field is accepted. The public profile is observable at runtime and ignored in source control.
- `validateSparkProfile(raw, allowlist): Readonly<SparkProfile>` accepts an exact matching separately pinned allowlist entry. `sparkRecoveryKey(profile, uid, legacyKey): string` binds mode/project/instance/UID; local key construction is unchanged. API-origin changes require a new explicitly approved allowlist and recovery decision, never automatic replay.
- `SparkServerConfig` is private: `{schema:'iilas-spark-server-1.0', profileSha256, credentialPath, credentialSha256, evidenceRoot, evidenceRootId, servingBindingPath, servingBindingSha256}`. The root ID is persistent UUIDv4. Source/model/adoption pins are in the bound serving file. CLI OAuth tokens are not an allowed credential. A separate closed `SparkLoopbackTestRuntime` is `{schema:'iilas-spark-loopback-test-1.0', mode:'spark-loopback-test', projectId, backendInstanceId, apiOrigin:'http://127.0.0.1:8011', webOrigins:['http://127.0.0.1:5173'], emulatorHosts:{auth:'127.0.0.1:9099',firestore:'127.0.0.1:8081',storage:'127.0.0.1:9199'}}`. Its private launch receipt additionally binds an owned evidence root and serving pins. `validateSparkLoopbackTest(raw)` validates this exact tuple; it has no cloud credential or production profile and is never tunnel/deploy eligible. Client transport accepts the validated production or loopback-test type; only the latter explicitly connects Auth/Firestore emulators and uses the loopback API. It has its own named SDK/recovery namespace and cannot masquerade as a cloud check.
- `createMsiBackend({runtime, verifyIdToken, executeCommand, evidenceRoutes, clock}): http.Server` exposes only `GET /health`, `POST /v1/command`, `PUT /v1/evidence/{web|mobile}/{intentId}/bytes`, `GET /v1/evidence/{evidenceId}/bytes`, `GET /v1/customer-proof/{shipmentId}`, and valid preflights. IDs are canonical existing validated identifiers; reject separators, percent-encoded traversal and unknown routes. Health returns only `{ready:boolean}` and never queries Firestore or loads a model.
- Command body remains exactly `{action,input}`. Protected requests carry `Authorization: Bearer <Firebase ID token>`, `X-IILAS-Protocol: iilas-msi-api-1.0` and `X-IILAS-Backend: <instance UUID>`; replies echo protocol/instance. Token subject alone supplies actor identity. Success is `{data:<existing result>}`; failure is `{error:{code,message,details?}}`, with existing public recovery details only. Codes are unprefixed Firebase semantic codes; web adapter exposes `functions/<code>` for existing callers. HTTP400invalid-argument,401unauthenticated,403permission-denied,404not-found,409already-exists/aborted/failed-precondition,429resource-exhausted,503unavailable,504deadline-exceeded; other errors are sanitised500internal.
- CORS allows only exact configured origins, supported route methods and headers above plus `Content-Type` and documented provider bypass header if needed. No cookies, query tokens, redirects or automatic POST retry. Absent Origin is allowed only with the same protected-request verification; an explicit unknown Origin fails. Private JSON and byte responses are no-store/nosniff.
- `EvidenceProvider`: `getMetadata(path): Promise<EvidenceMetadata>`, `download(path): Promise<Buffer>`, `createReadStream(path): Readable`. `EvidenceMetadata` carries `{path,size,contentType,generation,metadata}` with decimal-string generation, exact existing custom metadata and bounded bytes. `createMsiEvidenceStore({root,rootId,clock,diskFree}): EvidenceProvider & {commit(intent,stream):Promise<EvidenceMetadata>,audit():Promise<StoreAudit>,cleanupOwned(expiredIntent):Promise<CleanupResult>}`. `StoreAudit` is `{committed:number,quarantined:number,bytes:number}`; `CleanupResult` is `{removed:boolean,reason:'removed'|'referenced'|'not-expired'|'changed'|'unknown'}`. Writes are private; no URL generation or client-selected filesystem path.
- New web command `prepareEvidenceUpload` input is `{operationId,shipmentId,expectedVersion,evidenceId,stage,evidenceType,contentType,bytes,sha256,captureSource,capturedAtClient}` using existing domain validators. It returns `{intentId,path,metadata,expiresAt}` with scope/actor/version derived and bound on the server. Intent ID is64lowercase hex. Web intent lifetime30minutes; expiration blocks new upload but preserves exact committed-byte recovery. Mobile preparation keeps its existing lifetime/authority rules and returned ID. Existing registration/finalisation commands retain their original IDs and payload semantics.
- New private `msiEvidenceIntents` records deny all direct client access. Resolve the mobile upload ID only through its existing actor-bound `mobileEvidenceRequests` record. Both map to immutable provider metadata; uploading never registers evidence or changes delivery status by itself.
- All QA scripts added here have a no-argument focused-test mode producing sanitised pass/fail counts. Actual acceptance scripts additionally take `--profile <ignored-receipt>` and `--receipt <new-ignored-output>`. Staging/deployment CLI shapes are specified in Task8. No QA filename is evidence that the case passed.
