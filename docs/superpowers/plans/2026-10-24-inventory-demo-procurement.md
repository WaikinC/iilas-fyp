# Demo purchase orders and expected incoming stock Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Connect an independently accepted demo reorder requirement to an explicitly prepared, independently approved purchase order and trace its issue and physical receipts through expected incoming stock.

**Architecture:** Extend the existing purchasing lifecycle through one shared transaction implementation. Add immutable accepted-source proof, a permanent one-order link, private operation receipts and issue-time expected records; keep old unlinked purchasing compatible. The interface reuses the existing editor and action dialogs with a separate recoverable client.

**Tech Stack:** React/TypeScript, Node 22.13+ within major 22, Firebase Auth/Firestore/Functions emulators, existing Python/scikit-learn frozen RF14, JDK 21 and existing browser-test tooling. No new package or model dependency.

**Spec:** [Approved design](../specs/2026-10-24-inventory-demo-procurement-design.md), approved by the user on 24 October 2026. Native execution remains selected.

## Global Constraints

- Existing Submitted/Rejected/Approved/Issued/PartReceived/Received/Cancelled lifecycle; one product line and one permanent PO link per accepted requirement. Cancellation does not release the link. No legacy backfill.
- Human-entered supplier, quantity, MYR cost, expected date and reference; no AI suggested quantity, automatic order, approval, issue, receipt or supplier message. Requirement acceptance is separate from purchase approval.
- Preserve current role policies, selected initial Admin, IDs/balances, approved-staff shared scope, location accounting, Prepared-Shipment Handover and navy/purple eight-card dashboard.
- Exact account/scope-bound recovery for Create and every linked Resubmit/Approve/Reject/Issue/Cancel/Receive. Save before send; 35-second observation; unknown exact resolution creates a durable operation tombstone. No model/supplier HTTP inside purchasing transactions.
- All reads precede writes. Recheck current authority on every transaction attempt. Final new-creation capability check follows all reads. Linked actions/recovery always require the exact local emulator tuple; admitted orders can proceed when creation capability is disabled.
- New owner-scoped views use 20-row stable pages. Public scoped reads only, no direct client writes including Admin; private operation receipts deny all client access.
- Keep original experimental provenance false/null after human purchasing decisions. No retraining, consumed scientific TEST replay, genuine-readiness promotion, camera, other AI or extra features.
- Literal browser origin http://127.0.0.1:5173 or http://localhost:5173; one emulator stack, sequential Firebase suites. No production action.
- Dot-source ../Enter-IILAS.ps1; use npm.cmd/npx.cmd and the designated research Python. Preserve resource ceilings: one worker, two threads, 15-second execution plus 3-second drain, 2 GiB sampled worker RSS, 3 GiB free startup RAM and 1 GiB free disk.
- Keep this existing dirty checkout and ignored evidence. No worktree, staging, commit, push, merge or deployment. Checkpoints/ledger replace generic commit steps. Never display secrets or upload datasets, models, profiles, exports or test records.

## Review Focus

1. A saved Create/Resubmit reply is recovered after its expected date passes, product disappears and creation capability is disabled: return the original outcome; do not revalidate fresh admission before replay (Tasks 1/3/4).
2. A first partial receipt changes product facts: the second receipt still succeeds, while a changed product before first PO creation fails and preserves the accepted requirement (Task 3).
3. A plausible retained Accept event contradicts its requirement summary: reject new purchasing and show unavailable evidence without rewriting history (Tasks 1/3/4).
4. An old client reply arrives after account A→B→A or after the same client is disposed/reactivated: it cannot clear or replace the newly saved operation (Task 4).
5. Concurrent Issue/Receive/Cancel or a failure after a stock write cannot leave duplicated movements, inconsistent expected quantities or a successful private receipt for an uncommitted action (Tasks 2/3/6).

Derive it by existing validation plus explicit wire-field projection; never feed derived fields into the closed wire validator. Thus retry/resolve identity survives midnight.
- `ProcurementOutcome = {state:'Completed'|'Cancelled',operationId,kind,purchaseOrderId,eventId,status,version,replayed}`. Completed contains the committed order ID, existing `${orderId}_${version}` event ID, Create status Submitted/version1; Action version input.version+1 and status matching its step (Receive permits PartReceived or Received). Action order ID must match input. Cancelled has null order/event/status/version. Replay returns the original result, not latest PO status.
- `DemoProcurementSource = {version:1,policyVersion:'demo-procurement-1.0',requirementId,alertId,experimentId,review:DemoReviewSummary,basis:RiskBasis,provenance:ContextProvenance}`. All three IDs equal the original experiment ID; review is an independently Accepted version2 summary. Store this exact object as PO `demoReorderSource`; compute `sourceSha256 = SHA256(canonicalInventoryAI(source))`. Never change its contents during later transitions.
- `DemoProcurementLink = {version:1,ownerId,requirementId,purchaseOrderId,sourceSha256,createdBy,createdAt,dataOrigin:'demonstration-test'}` at requirement ID. Permanent and immutable, including after PO cancellation.
- `ExpectedReplenishment = {version:1,ownerId,purchaseOrderId,requirementId,source:DemoProcurementSource,sourceSha256,product:{productId,name,sku},supplier:{supplierId,name,contact},orderedQuantity,receivedQuantity,outstandingQuantity,expectedDate,orderVersion,state:'Expected'|'PartReceived'|'Received',createdAt,updatedAt,dataOrigin:'demonstration-test'}` at PO ID. Source carries review/experiment/model identity. Quantities are whole units within existing bounds, outstanding=ordered−received; state/orderVersion/quantities must match the current linked PO.
